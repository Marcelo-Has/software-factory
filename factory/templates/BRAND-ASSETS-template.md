# The brand-assets convention

## How to instantiate

Copy this file to `project/design/BRAND-ASSETS.md` at the start of the Foundation phase (see
`factory/docs/AUTONOMY.md` §2), before proposing anything in `DESIGN.md`. Then:

1. Create the `design/assets/` directory described below, at the repo root, even if every
   subpath in it stays empty.
2. Run the inventory scan in "Current state — inventory" below against the actual repository,
   and fill in the results table — verified, not assumed.
3. Keep this file live: update the inventory whenever new brand material lands in
   `design/assets/`, and note the date.

---

## What this is

The convention that makes a factory-wide requirement real: **a design system is born from
existing brand assets when they exist** — logos, images, colors, wireframes/Figma links, in a
directory the Foundation reads — with the provenance recorded in `DESIGN.md`.

**Why this exists.** Without an agreed-upon place, the Foundation invents a palette while the
product's logo sits in the owner's folder somewhere else. The result isn't just rework: it's a
design system that **contradicts the brand that already exists.** A directory with a fixed
address turns "check for an asset" from good intentions into a mandatory step of the process.

---

## The rule, in one sentence

**An existing asset is the primary source. Creating from scratch is only for what's proven
absent — and the Foundation proves the absence by reading `design/assets/` before creating
anything.**

## The directory

`design/assets/` lives **at the repository root**, not inside `project/docs/` and not inside
a served-assets directory. It's design raw material, not documentation and not an asset the
app serves — what the app publishes still comes from the normal build pipeline.

```
design/assets/
├── README.md        ← points to this convention
├── logos/           ← the brand in vector form when it exists; variants (positive, negative, icon)
├── images/           ← product photos and images already live or already approved
├── palette.md        ← colors that already exist, with the hex and WHERE each is already used
└── references.md     ← links: wireframes, Figma, reference products, moodboard
```

**`palette.md` and `references.md` are purpose-built markdown.** A color with no note on
where it's already used isn't an asset — it's a loose hex code, and a loose hex code is
indistinguishable from a guess. The same goes for a link with no sentence saying what's wanted
from that reference.

## What the Foundation does with this

A mandatory step, **before** proposing anything in `DESIGN.md` (see `factory/docs/AUTONOMY.md`
§2):

1. **Read all of `design/assets/`.** All four items, even the empty ones.
2. **Derive first.** Color, typography, shape, and tone that can come from an existing asset
   come from it. The `DESIGN.md` §4.1 palette is born from `palette.md` and the logos when
   they exist.
3. **Only create what's missing**, and record why it was missing.
4. **Record the provenance** of every decision in `DESIGN.md` §14 —
   `derived-from-asset`, `created-in-Foundation`, or `inherited-from-existing-DS`, with the
   source cited (see `factory/templates/DESIGN-template.md`).
5. **List what was read** in that same §14: the assets found as of the Foundation's date.
   That list is what justifies every `created-in-Foundation` row — without it, there's no way
   to tell "no asset existed" from "didn't look."

**A decision marked `created-in-Foundation` where an asset was actually available is a
violation of this convention**, and it's a `design-critic` review finding, not a matter of
preference.

## What goes in and what doesn't

**In:** the logo and its variants; photos and images already used in production; colors
already live; wireframes and Figma links; reference products with a sentence on what's taken
from them; any brand material the owner has already approved outside the repository.

**Not in:** an asset generated by the AI itself without approval (that's born in `DESIGN.md`,
not here, and its origin is `created-in-Foundation`); material with third-party rights the
project can't use; a real user's photo or anything derived from it — the repository **never**
versions customer material.

will already have been proposed without it, and reconciling means a new Decision Gate.
