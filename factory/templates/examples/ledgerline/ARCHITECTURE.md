## 1. System overview

Ledgerline is a web app backed by a BaaS-managed relational database and authentication
provider, with one outbound integration: an abstract external payment provider used both for
per-invoice payment collection and for Pro subscription billing. No background worker or
queue is needed for v1 — payment confirmation arrives synchronously via a verified webhook.

---

## 2. Stack decision — factory recommendation x owner preference

**Context:** a small team (one to a handful of engineers), a guided-flow-plus-dashboard
interface category (invoice list, invoice editor, settings, billing), a v1 budget that favors
managed infrastructure over operating a custom backend, and one external payment integration
that needs a webhook endpoint.

| Dimension | Factory recommendation | Reason | Owner decision | Owner's reason (if override) |
| --- | --- | --- | --- | --- |
| `frontend` | `frontend/sveltekit` | Matches the guided-flow-plus-dashboard category; component-scoped CSS fits a small, identity-driven UI without a heavy component-library dependency | accepted | — |
| `backend` | `backend/baas-supabase` | A BaaS backend removes the need to operate a custom API server for a product this size; row-level security fits the "owned by account" data-scoping rule in `DATA-MODEL.md` | accepted | — |
| `data-auth` | Bundled with `backend/baas-supabase` (managed Postgres + built-in auth) | Same BaaS provider covers both dimensions, avoiding a second vendor and a second auth integration to maintain | accepted | — |
| `deploy` | `deploy/netlify` | Matches the frontend module's deployment target; the core's existing preview-URL adapter works against it out of the box | accepted | — |

**Consequences:** the product commits to the chosen BaaS provider's row-level security model
for authorization instead of a hand-rolled authorization layer (see `nfr.md`'s authorization
matrix, which is expressed as policy per role rather than as custom middleware); the payment
webhook endpoint runs as a BaaS edge function rather than a standalone server route.

**Recorded in:** `project/state/profile.json` (illustrated here in prose; the file itself is
not part of this document set).

## 3. Architecture Decision Records

### ADR-1 — Payment confirmation via a verified webhook, never by polling

**Context:** an invoice or a subscription needs to know when the external payment provider has
actually been paid, without the client blocking on a slow synchronous payment call.
**Decision:** the payment provider calls a dedicated webhook endpoint on success; Ledgerline
verifies the provider's signature before trusting the payload, and treats a repeat delivery of
the same event id as a no-op (see `nfr.md` §3, idempotency).
**Consequences:** the webhook route is the one endpoint reachable without a logged-in session,
so its authorization model is "signature-verified, not user-authenticated" — a deliberate
exception recorded explicitly in `nfr.md`'s authorization matrix, not a silent gap in it.
**Status:** accepted

### ADR-2 — One workspace per account, no cross-account data sharing in v1

**Context:** `PRODUCT.md` §5 explicitly defers multi-user roles beyond owner/member and
shared client lists across teams.
**Decision:** every invoice, client, and settings record is scoped to exactly one account
(see `DATA-MODEL.md` §1's "owned by" column); there is no data model concept of sharing a
client or invoice across two accounts.
**Consequences:** simplifies the authorization matrix to two roles (`owner`, `member`) instead
of a general permissions system; revisiting this later means a genuine data-model migration,
not a settings toggle — the cost this ADR accepts on purpose, in exchange for v1 simplicity.
**Status:** accepted

## 4. API surface overview

A REST-shaped API generated by the BaaS backend plus one custom edge function for the payment
webhook. Named here in prose only, as candidate `operationId`s — the gated contract lives in
`contracts/openapi.yaml`:

- `listInvoices`, `createInvoice`, `getInvoice`, `updateInvoice` — invoice CRUD (F-1, F-2).
- `sendInvoice` — moves an invoice from `draft` to `sent`, triggers the email (F-3).
- `handlePaymentWebhook` — the payment provider's confirmation callback (F-3, F-5).
- `getAccountSettings`, `updateAccountSettings` — business info (F-4).
- `getSubscription`, `upgradeSubscription`, `cancelSubscription` — Pro plan management (F-5).

**External integrations:** `I-payments` — one abstract external payment provider, used for
both invoice payment links and subscription billing. Full contract in
`contracts/integrations.yaml`; definition guidance in
`factory/docs/playbooks/external-integration.md`.
